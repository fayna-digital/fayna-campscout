# ТЗ — Модуль розпізнавання облич учасників («face-index») для порталу таборів

**Дата:** 2026-08-04 · **Модуль-господар:** `fayna_camp_portal` (Odoo 17.0) · **Статус:** чернетка, чекає «ок»
**Рішення власника (04.08):** біометрія — Dodatek 4c з постійними векторами · постійний конвеєр на всі табори · дитина без 4a на груповому фото — блюр обличчя, фото лишається.

## 1. Мета і межі

**Мета.** Кадра заливає фото зі зміни → система сама пропонує, хто на кожному фото → після підтвердження людиною фото потрапляє в кабінет батька, і батько бачить кадри **своєї** дитини.

**У межах:**
- детекція облич, побудова біометричних шаблонів (embedding), пошук по еталонах;
- «навчальний» режим для іменних фото (дитина з підписом у кадрі) — саме такі 37 фото Пошумимо 2;
- зіставлення розпізнаного з `camp.participant` і запис у `camp.story.tagged_participant_ids`;
- автоблюр облич дітей без згоди 4a;
- RODO-шар: згода 4c, retention, право на видалення, журнал.

**Поза межами (окремі ТЗ):** відео, емоції/вік/стать, впізнавання кадри (тільки учасники), пошук по чужих фото з соцмереж.

## 2. Юридичний контур — обов'язковий, не опційний

Face-embedding для впізнавання конкретної дитини — `dane biometryczne w celu jednoznacznego zidentyfikowania osoby fizycznej`, тобто **art. 9 ust. 1 RODO** (особлива категорія). Наявна `image_consent` (Dodatek 4a) покриває **використання зображення** (art. 81 pr. aut.), а не біометрію. Це різні підстави, змішувати не можна.

**Що з цього випливає для коду:**

| Вимога | Реалізація |
|---|---|
| Окрема zgoda wyraźna, art. 9(2)(a) | **Dodatek 4c** — новий формуляр за зразком 4a/4b; поле `biometric_consent_state` на `camp.participant` |
| DPIA (art. 35) — біометрія + діти + систематична обробка | документ `docs/DPIA_face_index.md`, без нього модуль не вмикається на проді |
| Заборона обробки без згоди | **інваріант коду:** embedding не рахується й не зберігається, якщо `biometric_consent_state != "yes"` → `ValidationError` |
| Право на видалення (art. 17) | `action_erase_biometrics()` на учаснику: видаляє embeddings + enrollment-фото, лишає запис у журналі згод |
| Обмеження зберігання (art. 5(1)(e)) | cron: embeddings живуть до кінця сезону +N місяців (параметр), далі авто-видалення |
| Журнал | кожна дія — запис у `fayna.rodo.consent.log`, новий `purpose = child_biometrics` |
| Дитина без 4a у кадрі | автоблюр обличчя перед публікацією (рішення власника) |

⚠️ **Відкликання 4c ≠ відкликання 4a.** Дитина може лишитись на фото (4a=TAK), але зникнути з біометричного індексу (4c відкликано). Модель має тримати ці два стани незалежно.

### 2.1 Тестовий режим (діє зараз — рішення власника 04.08)

Dodatek 4c не збирається, тому **вимірювальний прогін іде без побудови біометричної бази**:

| Правило тестового режиму | Чому |
|---|---|
| embeddings рахуються **в пам'яті процесу й не записуються** ні в БД, ні на диск | немає біометричної бази → немає тривалого зберігання art. 9 |
| фото не покидають машину власника; сервіс слухає лише `127.0.0.1` | немає передачі третім особам |
| у звіті — **псевдоніми** («дитина №07»), імена лише в локальному мапінгу, який видаляється разом із прогоном | звіт не є персональними даними |
| артефакт прогону = метрики точності + перелік помилок, не прив'язки «обличчя→ім'я» | мета — оцінка придатності рушія, не ідентифікація |
| після зняття метрик — `rm` робочої теки прогону | обмеження зберігання |

Це **не** робить обробку неіснуючою — вона разова, локальна й мінімальна, чого достатньо для оцінки технології. **Умова виходу за межі тесту** (будь-який запис `camp.face.enrollment`, будь-яке автотегування реальних історій, будь-яка віддача батькам): зібраний Dodatek 4c + DPIA. Код мусить робити це неможливим механічно, а не покладатись на дисципліну — див. §7 гейтів.

## 3. Архітектура

Два процеси, чіткий кордон:

```
┌─────────────────────────────┐        HTTP (localhost)        ┌──────────────────────────┐
│  Odoo 17 · fayna_camp_portal│ ─────────────────────────────► │  face-service (Docker)   │
│  ─ моделі, згоди, черга,    │  POST /detect  {image}         │  Python + OpenCV DNN     │
│    підтвердження людиною,   │  → [{bbox, embedding, score}]  │  YuNet + SFace           │
│    RODO-гейти, блюр         │  POST /ocr     {image}         │  БЕЗ стану, БЕЗ БД       │
└─────────────────────────────┘  → [{text, bbox}]              └──────────────────────────┘
```

**Чому саме так:** сервіс не тримає жодних персональних даних — тільки рахує вектори й одразу забуває. Уся біометрія, згоди й журнал живуть в Odoo, під наявним RBAC і art.9-захистом (`models/art9_security.py`). Це різко зменшує площу RODO-ризику і дає змогу вимкнути/оновити рушій, не чіпаючи дані.

Сервіс не виставляється назовні — слухає тільки в docker-мережі.

## 4. Стек і ліцензії

| Компонент | Вибір | Ліцензія | Джерело |
|---|---|---|---|
| Детекція облич | **YuNet** (`face_detection_yunet`) | **MIT** | [ПЕРЕВІРЕНО: `raw.githubusercontent.com/opencv/opencv_zoo/main/models/face_detection_yunet/LICENSE`] |
| Embedding | **SFace** (`face_recognition_sface`) | **Apache-2.0** | [ПЕРЕВІРЕНО: той самий шлях, `face_recognition_sface/LICENSE`] |
| Репозиторій моделей | `opencv/opencv_zoo` | Apache-2.0, 1006★, push 2026-05-28 | [ПЕРЕВІРЕНО: GitHub API] |
| Рантайм | `opencv-python` (`cv2.FaceDetectorYN` / `cv2.FaceRecognizerSF`) — обидві моделі вбудовані в OpenCV | Apache-2.0 | — |
| OCR підписів | `tesseract` (ukr+pol) — уже використовується в `dokumenty`-пайплайні | Apache-2.0 | — |

**Чому НЕ InsightFace/ArcFace/buffalo_l** — попри те, що вони точніші: ваги моделей ліцензовані «for non-commercial research purposes only» [джерело: `deepinsight/insightface` python-package README]. Для комерційного продукту це прямий конфлікт. Код MIT, а ваги — ні; беруть саме ваги.

**Чому НЕ CompreFace** — 2 роки без push (останній 2024-10-05), тягне Java+Postgres збоку, і за замовчуванням FaceNet-ваги з невизначеною ліцензією тренувальних даних.

**Чому НЕ C++** — виграшу немає. Важка математика все одно виконується в C++-ядрі OpenCV/ONNX Runtime незалежно від мови хоста; Python додає лише host-side overhead на виклик. Бенчмарк порядку: SCRFD-детекція на CPU ~28 мс на 640×480, SeetaFace MobileFaceNet ~9 мс на обличчя. Навіть за песимістичних 100 мс/фото 3 000 фото сезону = ~5 хв пакетної обробки. Вузьке місце — не мова, а роздільність детектора й кількість потоків.

## 5. Моделі даних (Odoo)

**Розширення `camp.participant`** (дзеркало наявного блоку 4a, `participant.py:833-870`):
```
biometric_consent_state      Selection pending/yes/no, tracking, default pending
biometric_consent_signed_date / _signed_ip / _signature / _rodo_id
face_enrollment_ids          One2many → camp.face.enrollment
face_enrollment_count        Integer, computed
```

**`camp.face.enrollment`** — еталон дитини:
```
participant_id  M2o camp.participant (required, ondelete cascade)
attachment_id   M2o ir.attachment (вихідне фото)
bbox            Char "x,y,w,h"
embedding       Binary attachment=True (128-D float32 SFace)
model_version   Char (напр. "sface_2021dec")
quality_score   Float (різкість/розмір/фронтальність)
source          Selection: named_photo / manual / confirmed_detection
state           Selection: active / superseded / erased
```

**`camp.photo.batch`** — партія фото зі зміни: `event_id`, `group_id`, `uploaded_by`, лічильники, стан обробки.

**`camp.photo.detection`** — одне знайдене обличчя:
```
batch_id, attachment_id, bbox, embedding (тимчасовий),
candidate_participant_id, match_score Float,
ocr_caption Char (підпис, якщо був у кадрі),
state: proposed / confirmed / rejected / no_consent
confirmed_by, confirmed_date
```

**`camp.story`** — без змін схеми: модуль лише заповнює наявне `tagged_participant_ids`, і наявний гейт `_check_image_consent_before_publish()` (`stories.py:170-189`) починає працювати автоматично.

## 6. Пайплайн

### 6.0 Калібрувальна серія — інструмент для виховника (рішення власника 04.08)

«Іменна серія» стає **штатною процедурою зміни**: кожен виховник отримує завдання зняти 5-6 кадрів на дитину за заданими ракурсами. Це не побічна функція, а окремий екран у порталі.

**Умови роботи, які диктують конструкцію:** ліс, телефон, сонце в екран, інтернет може бути відсутній годинами. Тому:

| Вимога | Реалізація |
|---|---|
| Працює з телефона | мобільний веб `/my/kalibracja`, камера через `<input capture>`, великі цілі дотику |
| Працює **без інтернету** | кадри лягають у локальну чергу (IndexedDB) і синхронізуються, коли зʼявиться мережа — перевикористати патерн `static/src/kadry/draft_beacon.js`, який у модулі вже є |
| Виховник одразу бачить, чи кадр придатний | перевірка якості **на місці**, до відправки (див. нижче) |
| Видно, кого ще не знято | прогрес по групі: 24 дитини × 6 кадрів, лічильник і список «лишилось» |
| Не плутати дітей | вибір дитини зі складу **своєї групи**, з фото-аватаром, а не введення імені руками |

**Шість ракурсів серії** — підібрані під те, що реально ламає впізнавання на цих фото (діти в кепках, капелюхах, хустках, окулярах):
1. фронтально, без головного убору, нейтральний вираз;
2. фронтально, **у головному уборі**, як ходить у таборі;
3. ¾ поворот ліворуч;
4. ¾ поворот праворуч;
5. природне освітлення надворі — обличчя в тіні або проти сонця;
6. звичайний «живий» кадр — як дитина виглядає на щоденних фото.

**Контроль якості на місці** (рахує `face-service`, відповідь до 1 с; за відсутності мережі — базові перевірки на клієнті):

| Перевірка | Поріг | Повідомлення виховнику |
|---|---|---|
| обличчя знайдено рівно одне | =1 | «У кадрі кілька людей — зніми дитину окремо» |
| розмір обличчя | ≥112 px по меншій стороні | «Підійди ближче — обличчя замале» |
| різкість (варіація Лапласіана) | вище порогу калібрування | «Змазано — перезніми» |
| фронтальність (за 5 landmarks YuNet) | у межах ракурсу завдання | «Поверни трохи більше вліво» |
| засвіт/темрява | середня яскравість у коридорі | «Стань так, щоб сонце було збоку» |

**Нова модель `camp.face.calibration.task`:** `event_id`, `group_id`, `wychowawca_id`, `participant_id`, `required_shots` (default 6), `done_shots` (computed), `state` (todo/partial/done/skipped), `skip_reason`. Дає кадрі список, а керівнику — картину «група 1: 18/24 дітей відкалібровано».

🔒 **Гейт:** завдання створюється **тільки** для дитини з `biometric_consent_state == "yes"`. Немає 4c — дитина в списку не зʼявляється взагалі, а не «зʼявляється і падає при збереженні». У тестовому режимі (§2.1) екран доступний лише на `test_camp` з демо-складом.

### 6.1 Enrollment (навчання) — з іменних фото
1. Партія фото → `/detect` → список облич з bbox.
2. `/ocr` → burned-in підписи з їхніми bbox.
3. **Зіставлення підпис↔обличчя за геометрією:** найближче обличчя по горизонталі, підпис зазвичай під/над людиною. Кілька підписів у кадрі — кожен матчиться окремо; конфлікт → усі в чергу ручного розбору.
4. Ім'я з підпису → кандидат `camp.participant`, **пошук обмежений складом турнусу** (`event.registration` цієї `event_id`) — це головний важіль точності: шукаємо серед 24 дітей, а не 200.
5. Черга підтвердження людиною → на «підтвердити» рахується embedding і створюється `camp.face.enrollment`.
6. **Жодного автозапису без людини.**

### 6.2 Recognition (робочий режим)
Нові фото → детекція → embedding → косинусна відстань до еталонів турнусу → кандидат зі score → черга підтвердження → `tagged_participant_ids`.

Пороги (початкові, калібруються на тестовому наборі): `≥0.40` — авто-пропозиція; `0.28–0.40` — «непевно», у чергу з підсвіткою; `<0.28` — не пропонувати.

### 6.3 Публікація
Перед публікацією історії: для кожної підтвердженої дитини з `image_consent_state != "yes"` — **автоблюр** її bbox на похідній копії; в кабінет батьків іде копія, оригінал лишається в backend під art.9-правами.

## 7. Зіставлення імен — головна нетехнічна складність

На реальних даних підпис і реєстр розходяться систематично:

| Підпис на фото | Кваліфкартка | Клас розбіжності |
|---|---|---|
| Марта Городина | `43569_…Marta_Horodko` | різне прізвище (не транслітерація!) |
| Лея | `45153_…Lileia_Novichenko` | зменшене ім'я |
| Назар / Назар Тризна | `45170_…Nazarii_Tryzna` | форма імені + транслітерація |
| Василій / **Висилій** | `45284_…Vasylii_Moiseienko` | описка автора підпису |
| Віталій | — | у 24 картках відсутній (Petska, поза списком) |

**Алгоритм:** транслітерація UA→LAT (паспортна КМУ) → нормалізація (нижній регістр, і/и/й, є/e) → Jaro-Winkler по імені та прізвищу окремо → словник зменшених форм (Лея↔Лілея, Соломія↔Solomiia) → **обмеження складом турнусу**. Score нижче порогу — не вгадувати, а класти в чергу «ім'я не впізнано».

Правило, яке кодуємо явно: **збіг імені — це кандидат, не факт.** Запис у базу тільки після людини.

| 5 | Автоблюр + віддача в кабінет батьків | `/my/camp-day` показує тільки свою дитину | після 4 |
| 6 | Retention-cron + `action_erase_biometrics` | RODO-замикання | разом з 1, добудова після 4 |

Етап **T** ні від чого не залежить і не чіпає Odoo — з нього і починаємо. Етапи 1+ стартують лише після 0. На прод — тільки через staging, окремим «ок» (#ОК-ПРОД).

## 10. Сховище фото і «альбом дитини за сезони» (рішення власника 04.08 — потрібне окреме місце)

Мета власника: батько відкриває кабінет і бачить **фотоальбом своєї дитини за всі сезони**, а не купу історій зміни.

### 10.1 Три різні строки, які не можна змішувати

Головна причина, чому альбом за 3 сезони взагалі можливий: **фото і біометричний шаблон — різні дані з різними підставами і строками.**

| Що | Підстава | Строк | Що вмикає видалення |
|---|---|---|---|
| **Embedding** (біометричний шаблон) | art. 9(2)(a), Dodatek **4c** | поки дитина активний учасник **+12 міс** (щоб наступного сезону не калібрувати заново) | відкликання 4c → **негайно**; вихід з таборів → після 12 міс cron |
| **Фото** (wizerunek) | art. 6 + art. 81 pr. aut., Dodatek **4a** | доки діє доступ батька до кабінету + строк за umową | відкликання 4a → фото прибирається з кабінету |
| **Тег** (звʼязок фото↔дитина) | похідне | живе з фото | відкликання 4a → тег знімається, фото лишається (з блюром) |

Тобто «видалили embeddings» **не** руйнує альбом: підтверджені теги вже записані, і альбом будується з них, а не з векторів. Це і є відповідь на «а якщо дитина у нас 3 сезони».

### 10.2 Де фізично лежать фото — не Google

**Проти Google Drive як сховища:**
- фото дітей у чужій хмарі = передача даних процесору, потрібен DPA і оцінка трансферу — рівно та зона ризику, яку весь §2 намагається прибрати;
- залежність від зовнішнього API для показу альбому в кабінеті;
- окремо: рахунок Google Workspace зараз проблемний [ПЕРЕВІРЕНО: memory `project_campscout_google_workspace_payment_declined_2026-08-01`] — вішати на цей канал альбоми дітей не варто.

**Рекомендація — своє сховище, у три деривативи на кожне фото:**

| Дериватив | Розмір | Кому | Де |
|---|---|---|---|
| `original` | як знято | архів, backend, art.9-права | filestore, поза кабінетом |
| `web` | довга сторона ~1600 px | альбом батька | filestore, через `/web/image` з access_token |
| `thumb` | ~400 px | сітка, швидке гортання | filestore |

Odoo зберігає бінарники `ir.attachment` **у filestore на диску**, а не в БД, і робить дедуплікацію за checksum — тобто той самий кадр, прив'язаний до пʼятьох дітей, лежить на диску один раз. Це знімає більшу частину проблеми обсягу без нової інфраструктури.

**Оцінка обсягу** [ПРИПУЩЕННЯ, рахунок від реального: ці 37 фото = 220 КБ середнє, стиснуті; оригінал з телефона зазвичай 3-4 МБ]: зміна ~1 500 кадрів → ~0,3 ГБ у web-якості або ~5 ГБ оригіналами; сезон з 4 змін → ~1,3 / ~20 ГБ; три сезони → ~4 / ~60 ГБ. Тобто звичайний диск сервера тримає це роками — окреме об'єктне сховище стає потрібним не одразу.

**Коли переростемо диск:** винести filestore на S3-сумісне сховище в ЄС (напр. Hetzner Object Storage) **монтуванням на рівні інфраструктури**, без Odoo-модуля і без зміни коду.

⚠️ **OCA/storage брати не можна.** Модуль існує, живий і має гілку 17.0 [ПЕРЕВІРЕНО: GitHub API, push 2026-08-03], але ліцензія **AGPL-3.0**, а `fayna_camp_portal` — **OPL-1** [ПЕРЕВІРЕНО: `__manifest__.py:5`]. `depends` на AGPL-модуль зобов'язує розкрити наш код. Тому — або mount на рівні інфраструктури, або тонкий власний адаптер, але не залежність від AGPL.

### 10.3 Модель альбому

`camp.photo.album` — **персональна одиниця**, окремо від `camp.story` (та лишається редакційною: «історія зміни»):
```
participant_id  M2o camp.participant
season_id / event_id
photo_ids       M2m ir.attachment (через підтверджені camp.photo.detection)
cover_id, photo_count
```
Кабінет: `/my/album/<participant_id>` — фото згруповані за сезонами й змінами. Показуються **тільки** кадри, де дитина підтверджена людиною і `image_consent_state == "yes"`; чужі діти без 4a у тих самих кадрах — з блюром (§6.3).

## 10.4 Відео — окремий контур, не «фото ×N» (уточнення власника 04.08: до 1500 фото + відео зі зміни)

**Реальні цифри, зміряні на наявних файлах** [ПЕРЕВІРЕНО: `mdls` по `~/Downloads/IMG_0120.MOV`, `IMG_0121.MOV`]: H.264, 1072×1920, бітрейт ~10 Мбіт/с → **~71 МБ за хвилину** (114,1 МБ на 96,4 с; 73,0 МБ на 60,7 с — збіг стабільний).

### Обсяг зі зміни

| | оригінали | веб-версія |
|---|---|---|
| 1 500 фото | 4,5-6 ГБ [ПРИПУЩЕННЯ: 3-4 МБ/кадр з телефона] | ~0,45 ГБ (`web` ~300 КБ) |
| відео 30-120 хв | 2,1-8,5 ГБ (71 МБ/хв) | 0,45-1,8 ГБ (720p ~2 Мбіт/с ≈ 15 МБ/хв) |
| **зміна разом** | **~7-15 ГБ** | **~1-2,3 ГБ** |
| сезон (4 зміни) | ~28-60 ГБ | ~4-9 ГБ |
| три сезони | **~85-180 ГБ** | **~12-28 ГБ** |

Це і є справжня ціна питання «чи тримаємо оригінали» (§11): архів оригіналів росте на порядок швидше за те, що реально бачить батько.

### Три технічні наслідки

1. **Транскодування обов'язкове.** Вертикальне 1072×1920 на 10 Мбіт/с у `.MOV` не годиться для кабінету — потрібен MP4 H.264 720p + постер-кадр. `ffmpeg` **на машині відсутній** [ПЕРЕВІРЕНО: `which ffmpeg` → not found] — ставиться в образ `face-service`, не на хост.
2. **Розпізнавання по семплінгу, не по кадрах.** 120 хв × 30 fps = 216 000 кадрів — безглуздо. Беремо **1 кадр/с**: 120 хв → 7 200 кадрів → ~12 хв обробки при 100 мс/кадр. Дитина, впізнана хоч в одному семплі, тегується на все відео.
3. **Блюр на відео — головна пастка, і його на старті НЕ робимо.** Для фото блюр — один рендер. Для відео це трекінг обличчя по всіх кадрах + повний ре-енкод; втрата треку на кількох кадрах = обличчя «блимає» незаблюреним, тобто порушення при формально «зробленому» блюрі.

   **Правило допуску замість блюру:** відео потрапляє в альбом, **тільки якщо всі впізнані на ньому мають 4a**. Є хоч одна дитина без 4a → відео в чергу ручного рішення (обрізати фрагмент або не публікувати). Чесно, дешево і не створює ілюзії захисту.

⚠️ **Юридичне, яке треба звірити з папером:** у коді 4a названо «zgoda na wizerunek», а docstring `sign_image_consent()` каже «image/**video** consent» [ПЕРЕВІРЕНО: `participant.py:1916`]. Самого тексту формуляра в репо немає — він у полі `image_consent_body` на `res.company` [ПЕРЕВІРЕНО: `participant.py:2393-2398`], тобто в БД. **Поки текст не прочитано, вважати, що 4a покриває відео, не можна** — це в §11.

## 10.5 Сімейний архів і повноліття (уточнення власника 04.08)

Сценарій власника: дитина їздить з 6 років щороку; народжується друга й теж починає їздити; перша досягає 18 і більше не їде, друга ще росте. Отже **кабінет живе 12+ років і тримає кількох дітей одночасно**, а не «сезон».

Технічна база для цього вже є: `camp.participant.parent_partner_id` [ПЕРЕВІРЕНО: `participant.py:115`] дає одному батькові кілька дітей, `birth_date`/`age` [ПЕРЕВІРЕНО: `participant.py:146,158`] дають вік. Бракує життєвого циклу.

### 10.5.1 Повноліття — момент, коли згода батька перестає діяти

Згоду 4a/4c за дитину дає opiekun. Коли дитині виповнюється 18, вона стає самостійним суб'єктом даних — і **згода батька за неї більше не є підставою**. Фото 18-річної людини в чужому (батьківському) кабінеті без її власного рішення стоїть на порожній підставі.

Рішення, яке водночас закриває RODO і дає бізнес-цінність — **архів переходить до самої людини**:

| Крок | Коли | Що робить система |
|---|---|---|
| попередження | за 60 днів до 18-річчя | лист батькові й самій особі: «архів скоро перейде під твій контроль» |
| перехід | у день 18-річчя | `camp.participant.adult_transition_state = pending`; створюється власний портальний доступ для самої особи |
| рішення особи | будь-коли після | одне з трьох: **лишити доступ батькам** · **забрати архів собі** (батьки втрачають) · **видалити все** |
| якщо мовчить | 180 днів без відповіді | альбом ховається з батьківського кабінету (не видаляється), лишається доступним особі — тиша не є згодою |
| біометрія | **у день 18-річчя, без винятків** | `embedding` і `camp.face.enrollment` видаляються: згода 4c від батька більше не діє. Хоче далі — підписує 4c сама |

Побічна вигода: випускник табору отримує свій архів дитинства і власний кабінет — природний місток до «колишній учасник → вожатий → клієнт».

### 10.5.2 Скільки живе доступ родини

Прив'язувати не до «дитина активний учасник», а до відносин з родиною:

- альбом доступний батькам, доки **хоч одна дитина в родині була в таборі за останні 5 років**;
- після цього — лист «архів закриється через 90 днів»: можна **завантажити все ZIP-ом** (це ще й art. 20, переносимість) або продовжити доступ одним кліком;
- без реакції — альбом переводиться в архівний стан (не видаляється мовчки, але з кабінету зникає);
- явна вимога видалення від батька або від повнолітньої особи — виконується завжди й негайно.

Так альбом першої дитини не зникає, поки друга ще їздить, і не висить вічно, коли родина пішла.

### 10.5.3 Що з цього випливає для моделей

```
camp.participant:
    adult_transition_state   Selection none/pending/self_managed/parent_kept/erased
    adult_transition_date    Date (computed з birth_date + 18 років)
    own_portal_user_id       M2o res.users (доступ самої особи після 18)
camp.photo.album:
    access_state             Selection active/warned/archived
    last_family_activity     Date (computed: остання участь будь-якої дитини родини)
```
Крони: `_cron_adult_transition_warning` (‑60 днів), `_cron_adult_transition` (день 18), `_cron_family_archive_warning` (5 років), `_cron_family_archive` (+90 днів).

## 10.6 Рекламний фонд і оригінали (рішення власника 04.08: «для реклами треба щось завжди мати»)

### 10.6.1 Що насправді покриває 4a, а що 4b — звірено з бланком

Тексти прочитані дослівно з форми, яку підписують батьки:

**Dodatek 4a** [ПЕРЕВІРЕНО: `static/src/kadry/rodzice.html:94`, ідентичний текст у PDF-генераторі `:292`]:
> «Wyrażam zgodę / nie wyrażam zgody na użycie **zdjęć/wideo** mojego dziecka **do promocji CampScout** (strona, Instagram, Facebook, Telegram, broszury).»

**Dodatek 4b** [ПЕРЕВІРЕНО: `rodzice.html:103`]:
> «Wyrażam zgodę na otrzymywanie informacji o nowych turnusach, promocjach i aktualnościach CampScout **drogą elektroniczną (e-mail)**.»

Підтверджено й формулюванням підстав `rodzice.html:69`: 4a — `rozpowszechnianie wizerunku w celach promocyjnych`, 4b — `komunikacja marketingowa drogą elektroniczną`.

**Два висновки, обидва важливі:**

1. **Відео вже покрите** — «zdjęć/**wideo**» стоїть у самому тексті згоди, і саме «do promocji». Доповнювати формулювання не потрібно.
2. **Реклама з фото/відео стоїть на 4a, а не на 4b.** 4b — це email-розсилки батькам і до використання зображень стосунку не має.

| Призначення | Підстава | Оригінал потрібен? |
|---|---|---|
| Альбом у кабінеті батька | **4a** | ні, `web` достатньо |
| Фотокнига для родини | **4a** | так, на замовлення |
| **Реклама** — сайт, FB, Instagram, Telegram, брошури, **відео** | **4a** | **так, зберігати завжди** |
| Email-розсилка батькам | **4b** | — |

Станом на 31.07.2026 це означає, що проти рекламного використання — **2 родини з 63** (4a NIE), а не 12 [ПЕРЕВІРЕНО: memory `reference_campscout_zgody_rodo_rejestr_z_ocr_kartek_2026-07-31`: 4a TAK 61 / NIE 2; 4b TAK 51 / NIE 12 — це окремий, поштовий контур]. Фонд виходить майже повним.

### 10.6.2 Не «тримати всі оригінали», а вести відібраний фонд

Замість зберігання 1 500 оригіналів зі зміни — **курований рекламний фонд**:

```
camp.photo.marketing.pool
    attachment_id      оригінал у повній якості
    event_id, season_id
    selected_by        хто відібрав
    clearance_state    Selection: pending / cleared / blocked
    blocked_reason     Char
```

Кадра або маркетолог позначає кадр «у фонд» → кадр проходить **автоматичну перевірку допуску** → лише `cleared` можна використати назовні.

**Гейт допуску (механічний, за зразком `_check_image_consent_before_publish`):**

| Умова | Результат |
|---|---|
| `faces_detected == 0` — кадр без людей (природа, побут, спорядження) | `cleared` автоматично — найцінніший і найбезпечніший клас для реклами |
| `faces_detected == faces_tagged` **і** всі теговані мають **4a = TAK** | `cleared` |
| хоч одна тегована дитина має **4a = NIE** | `blocked` — «wizerunek NIE: <імена>» |
| **`faces_detected > faces_tagged`** — у кадрі є нерозпізнане обличчя | `blocked` — невідомо, чия дитина, отже невідомо, чи є згода |

**Інваріант, який кодуємо явно:** «немає тегу» ≠ «немає дитини». Допуск рахується від **рівності `faces_detected == faces_tagged`**, а не від самого лише переліку тегів — інакше кадр із чужою невпізнаною дитиною тихо пройде як «усі теговані мають згоду». Блюр тут не альтернатива: рекламний кадр із заблюреним обличчям не працює як реклама.

### 10.6.3 Що з обсягом

| Клас | Скільки | Строк оригіналу |
|---|---|---|
| рекламний фонд (відібране) | ~50-150 кадрів зі зміни → **0,2-0,6 ГБ** | **безстроково**, поки діє 4b |
| решта архіву | ~1 400 кадрів | оригінал живе 12 міс (на випадок фотокниги), далі лишаються `web`+`thumb` |
| відео | добірка кліпів у фонд | оригінал добірки безстроково, решта — 12 міс |

Замість ~85-180 ГБ за три сезони (§10.4) виходить **~15-30 ГБ**: веб-архів усього плюс повна якість тільки того, що реально використовується.

⚠️ **Відкликання 4a має чистити фонд, і це не теорія.** Батьки вже змінювали рішення в обидва боки — Mullier і Tymur Rudenko відкликали, Rachev ×2, Gotsman, Hrynishak навпаки додали [ПЕРЕВІРЕНО: та сама memory]. Cron: зміна 4a на NIE → усі кадри цієї дитини у фонді переходять у `blocked` і зникають зі списку доступного для реклами. Той самий cron знімає її теги з опублікованих історій і вмикає блюр (§6.3).

Окремо: **вже використаний зовні матеріал** (пост в Instagram, надрукована брошура) автоматично не відкликається — cron має ставити задачу людині зі списком «де цей кадр уже опубліковано», інакше «відкликано» буде правдою лише в базі.

## 10.7 Що вписати в umowę (рішення власника 04.08 — умову і так оновлюємо)

Умова оновлюється комплексно (скасування, форс-мажор, недобір груп — **поза цим ТЗ**). Нижче — рівно ті пункти, які потрібні цьому модулю, щоб строки зберігання й доступи мали договірну підставу, а не трималися на самій згоді.

| Пункт умови | Формулювання по суті | Навіщо |
|---|---|---|
| **Доступ до альбому** | Кабінет із фотоархівом дитини доступний Замовнику, доки хоча б одна дитина родини брала участь у таборі протягом останніх **5 років**; далі — повідомлення і **90 днів** на завантаження чи продовження | §10.5.2 без цього нічим не підпертий |
| **Переносимість** | Замовник у будь-який момент може завантажити весь архів дитини одним файлом | art. 20 RODO + практична цінність |
